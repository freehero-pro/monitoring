# Мониторинг доступности

Проверяет, что сайты и API живы и отвечают быстро, и показывает статистику на сайте
со входом по ссылке из письма.

- **Джоба** раз в заданный интервал дёргает каждый URL: измеряет DNS, TCP, TLS и время до
  первого байта, проверяет код ответа и содержимое, считывает срок действия TLS-сертификата.
- **Сайт** показывает текущий статус, uptime, p50/p95, историю проверок, инциденты и
  сертификаты. Администраторы заводят проверки прямо в интерфейсе.
- **Алерты** уходят webhook-ом при падении, восстановлении и скором истечении сертификата.

Стек: Node 22+ / TypeScript, Fastify, Postgres (Drizzle ORM), React + Vite + styled-components.
Один процесс выполняет и API, и планировщик; очередь проверок живёт в самом Postgres
(`FOR UPDATE SKIP LOCKED`), поэтому очередей и брокеров не нужно.

## Быстрый старт

```bash
cp .env.example .env          # укажите ADMIN_EMAIL, при желании SMTP
docker compose --profile dev up -d postgres mailhog
npm install
npm run db:migrate
npm run db:seed               # создаст администратора из ADMIN_EMAIL
npm run dev                   # API :3000, фронт :5173
```

Откройте http://localhost:5173, введите почту администратора. Письмо со ссылкой придёт
в MailHog: http://localhost:8025. Если SMTP не настроен, ссылка печатается в лог сервера.

Для разработки в `.env` должно быть `APP_BASE_URL=http://localhost:5173` — Vite проксирует
`/api` на сервер, поэтому cookie сессии работает как в проде.

## Продакшн

```bash
docker compose --profile prod up -d --build
```

Одна команда поднимает Postgres, приложение и Caddy: Fastify отдаёт API и статику фронта,
Caddy получает сертификат Let's Encrypt для домена из `APP_BASE_URL` и продлевает его сам.
Миграции применяются при старте.

Полная инструкция — [docs/DEPLOY.md](docs/DEPLOY.md): переменные окружения, HTTPS и
reverse proxy, первый администратор, обновление версии, резервные копии, диагностика.

## Пользователи

Регистрации нет — аккаунты заводятся вручную:

```sql
INSERT INTO users (email, role) VALUES ('dev@company.ru', 'viewer');
```

Роли: `admin` — редактирует проверки и каналы, `viewer` — только смотрит статистику.
Отключить доступ, не теряя историю: `UPDATE users SET is_active = false WHERE email = '…';`

Вход: пользователь вводит почту, получает письмо со ссылкой (действует 15 минут,
срабатывает один раз), после перехода получает cookie-сессию на 30 дней.
Ответ на запрос ссылки всегда одинаковый — по нему нельзя узнать, заведён ли аккаунт.

## Что умеет проверка

| Параметр | Смысл |
|---|---|
| Метод, заголовки, тело | Позволяет дёргать реальные эндпоинты, в том числе с авторизацией |
| Интервал, таймаут, повторы | Как часто, сколько ждать и сколько раз повторить при сбое |
| Неудач до инцидента | Сколько подряд неудач считать авариями (по умолчанию 2) — глушит одиночные всплески |
| Порог «медленно» | Ответ верный, но дольше порога → статус `degraded` |
| Ассерты | Код ответа, подстрока в теле, JSON-поле, заголовок, максимальное время ответа |
| Не проверять TLS | Для внутренних сервисов с самоподписанным сертификатом |

Если ассерты не заданы, успехом считается любой ответ с кодом ниже 400.

Статусы: `up` — норма, `degraded` — отвечает, но медленно, `down` — подтверждённое падение,
`unknown` — ещё не проверялась.

## Формат webhook

POST с JSON и заголовками `X-Monitoring-Event` и (если задан секрет)
`X-Monitoring-Signature: sha256=<HMAC-SHA256 тела>`:

```json
{
  "event": "incident.opened",
  "at": "2026-08-29T12:45:03.000Z",
  "check": { "id": "…", "name": "Сайт example.com", "url": "https://example.com", "tags": ["prod"] },
  "incident": { "id": "…", "startedAt": "…", "errorKind": "connect", "error": "connect ECONNREFUSED" }
}
```

События: `incident.opened`, `incident.resolved` (с `durationMs`), `cert.expiring`
(с `daysRemaining`). Три попытки доставки с нарастающей паузой; все попытки видны
в разделе «Каналы» и в таблице `webhook_deliveries`.

Канал, не привязанный ни к одной проверке, считается общим и получает события по всем.

## Хранение истории

Сырые результаты живут `RAW_RETENTION_DAYS` дней (по умолчанию 30), поверх них раз в пять
минут считаются часовые агрегаты (`check_stats_hourly`), которые не удаляются. Графики за
сутки строятся по сырым данным, за неделю и месяц — по агрегатам.

## Переменные окружения

Все перечислены в [.env.example](.env.example). Наиболее важные:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение к Postgres |
| `APP_BASE_URL` | Публичный адрес сайта; из него собирается ссылка в письме |
| `SMTP_*`, `MAIL_FROM` | Почта для magic-link; без `SMTP_HOST` ссылка идёт в лог |
| `ADMIN_EMAIL` | Кого создаст `npm run db:seed` |
| `SCHEDULER_TICK_MS`, `MAX_CONCURRENT_CHECKS` | Частота опроса очереди и параллелизм |
| `RAW_RETENTION_DAYS` | Сколько дней хранить сырые результаты |
| `TLS_WARN_DAYS` | За сколько дней предупреждать об истечении сертификата |
| `AUTH_IP_RATE_LIMIT` | Лимит запросов ссылки с одного IP в час |

## Разработка

```bash
npm test          # тесты сервера (нужен запущенный Postgres)
npm run typecheck # проверка типов сервера и фронта
npm run build     # сборка фронта и сервера
```

Тесты идут против настоящего Postgres: база `monitoring_test` создаётся автоматически
при первом запуске. Раннер тестируется на локальном http-сервере, который умеет тормозить,
падать и рвать соединение; https-тесты требуют `openssl` в PATH.

После изменения схемы в `server/src/db/schema.ts` выполните `npm run db:generate` —
drizzle-kit создаст SQL-миграцию в `server/src/db/migrations`.

## Структура

```
server/src
  runner/      выполнение проверок: коннектор с таймингами фаз, ассерты, планировщик
  checks/      CRUD проверок и выборка созревших из очереди
  alerts/      инциденты и доставка webhook
  auth/        magic-link, сессии, роли
  stats/       запросы для графиков, часовая агрегация, очистка истории
  db/          схема, миграции, сид
web/src
  pages/       вход, обзор, карточка проверки, форма, инциденты, каналы
  components/  графики, полоса доступности, разбивка по фазам
```
